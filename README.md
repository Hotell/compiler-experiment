# React Compiler vs manual memoization

Three standalone React 19 + Vite 8 + TypeScript incident triage consoles compare Oxc's experimental Rust React Compiler, explicit `useMemo`/`useCallback`/`React.memo`, and an unoptimized baseline. All three show the same 200 deterministic incidents and use identical DOM, CSS, icons, state transitions, and provider boundaries. No backend or live data is required. Similar committed-update counts are a valid result, not a failed benchmark.

## Hosted comparison

The [chooser](https://hotell.github.io/compiler-experiment/) links to the [compiler-on](https://hotell.github.io/compiler-experiment/compiler/), [manually optimized](https://hotell.github.io/compiler-experiment/manual/), [unoptimized baseline](https://hotell.github.io/compiler-experiment/baseline/), [compiled source comparison](https://hotell.github.io/compiler-experiment/sources/), and [latest successful benchmark report](https://hotell.github.io/compiler-experiment/report/) pages. On a commit/merge to the default branch, the `Benchmark` workflow runs first; **only a successful push-triggered run on that branch** starts the `Pages` workflow. Pages checks out the exact benchmarked commit, downloads that run's `compiler-comparison` artifact, and publishes the apps plus a styled report with flame charts and raw audits. A failed benchmark leaves the previous successful Pages deployment intact. GitHub Pages must use **GitHub Actions** as its build source.

The source comparison publishes formatted post-transform, pre-bundle JavaScript for the six first-party modules in each experiment. It defaults to compiler vs. baseline `App.js` and lets you compare any pair or module, with links to each raw output. Compiler and baseline compile the same shared sources independently; manual compiles its own `App` and `providers`. These snapshots expose compiler cache transforms without minification, but are inspection artifacts, not the shipped bundles: later bundling, environment replacement, dead-code removal, and minification can still change the runtime files. Normal production builds emit them without including them in shipped-byte totals. The benchmark captures the compiler/manual App snapshots; Pages verifies that its regenerated snapshots match the measured ones.

To preview the chooser and report locally from the repository root:

```sh
yarn benchmark:all  # Measure the three apps and the isolated row-memo experiment
yarn build:pages    # Assemble dist-pages from those results
yarn preview:pages  # http://127.0.0.1:4180/compiler-experiment/
```

Keep the preview command running while browsing. The local report is labeled as a preview; CI deployments link to the successful benchmark run. `node scripts/check-pages.mjs` tests the same assembled site without leaving a server running. `dist-pages` and benchmark results are generated and ignored.

### Before pushing and recovering deployments

The default pre-push hook runs lint and application type checks, not browser or deployment checks. For a complete local check before pushing, run:

```sh
yarn verify:push   # Fresh benchmarks + ablation, then assemble and exercise all Pages routes
git push
```

This takes several minutes. For site/check-only edits with matching benchmark provenance, use `yarn check:pages` instead; it rebuilds the deployed layout and runs the desktop/mobile and DevTools checks. Changed application sources, dependencies or benchmark inputs require `yarn verify:push` to regenerate measurements. Neither command uploads or deploys anything.

The `Benchmark` workflow now checks the publishable Pages site on **every push and pull request**, after measurement. Require its `compare` job in the default branch's ruleset to catch failures before merging; local hooks can be bypassed and macOS-only results do not guarantee Linux compatibility. The `Pages` workflow repeats the same `yarn check:pages` check on its fresh runner before publishing.

After pushing, use `gh run list --commit "$(git rev-parse HEAD)" --limit 5` to find the Benchmark and subsequent Pages runs. Watch each with `gh run watch <run-id> --exit-status`; a green Benchmark alone does not confirm the subsequent deployment completed. If Pages fails, inspect `gh run view <pages-run-id> --log-failed`. Navigation failures save `pages-failure-*.png` and Playwright traces in `benchmark/results/`; CI uploads them as `playwright-diagnostics` (Benchmark) or `pages-diagnostics` (Pages). Download with `gh run download <run-id> --name <artifact-name>`, then open a trace with `yarn playwright show-trace <trace.zip>`.

A deterministic source/test failure needs a fix and a new commit/push; rerunning the old workflow still checks out the old code. Only rerun failed jobs (`gh run rerun <run-id> --failed`) for a transient failure on otherwise valid code. The previous successful deployment remains live until the replacement passes.

## Isolated row-memo ablation

To measure the contribution of **only** the manual app's outer `memo(IncidentRow)` boundary:

```sh
yarn benchmark:row-memo
```

Open `benchmark/results/row-memo/report.html` in a browser (on macOS, `open benchmark/results/row-memo/report.html`). The HTML is self-contained and links to its raw `measurements.json` and computed `comparison.json`; `comparison.md` is available too. The experiment remains separate from the three comparison arms, but matching results are summarized in the main report and linked to a dedicated page at `report/row-memo/report.html`.

`yarn benchmark:all` runs both experiments and refreshes the combined report. To attach a separately rerun ablation to an existing matching main benchmark, use `node scripts/report.mjs` before `yarn build:pages`. A main-only `yarn benchmark` still works; absent or source/runtime-mismatched ablation results produce an explicit "Ablation unavailable for this build" notice, not a broken link. Incomplete or internally inconsistent evidence fails validation.

The main runner fingerprints application sources, build configuration, dependencies and benchmark workloads before building, then checks sources and built files again after measurement. `provenance.json` binds the source fingerprint, six builds and raw measurements. Both experiments use the same fingerprint, and attaching the ablation additionally requires its ON initial-load assets to be byte-identical to the measured manual build. Pages checks provenance and artifact integrity before copying either report; it never silently publishes old ablation results beside new main measurements. Regenerate measurements after changing fingerprinted inputs.

The command builds memo ON and OFF from identical source, for both normal production and React profiling, into `apps/manual/dist-ablation/{on,off}/{production,profile}`. `yarn build:row-memo` builds just those artifacts. The explicit `ROW_MEMO_ABLATION=on|off` build flag changes only the outer row wrapper; row callbacks, memoized child buttons, provider values, filtering, DOM and state transitions remain intact. Invalid flag values, non-build commands, unsupported modes and combining this flag with a Pages build are rejected. Ordinary builds with the flag unset retain row memoization. Each isolated build emits `ablation.json` with its arm, mode, React version and source fingerprint; the runner/report reject mismatched sources or build identities.

The dedicated runner uses ports 4371/4372 for native profiling and 4471/4472 for normal production. Profiling verifies row-work counts of ON `0/1/1` versus OFF `67/67/67` for queue switch, selection and favorite respectively, while open-button work stays zero and only the affected favorite button does work. It preserves actual/base durations separately. These checks confirm the intervention, not its performance benefit.

Production timings use 4x CPU throttling, three fresh-context blocks and ten paired trials per block, with one warm-up workflow per arm per block. Within each block, a recorded seeded shuffle balances five ON-first and five OFF-first trials. Both arms start each paired workflow from equivalent UI state; reset work is outside timing and snapshots are compared after every action. Timers measure click-handler-to-DOM readiness and a subsequent two-frame opportunity, not input delay, actual presentation or INP. Favorite history accumulates equally in both arms.

The report gives normal-build raw/gzip sizes and paired differences **OFF minus ON** (positive milliseconds favor memo). An exploratory 95% Student-t interval uses the three block mean differences, not 30 supposedly independent observations; it assumes independent/approximately normal block effects despite all blocks sharing one browser/hardware session. Three blocks provide weak uncertainty estimates, intervals are not adjusted for multiple endpoints, and an interval spanning zero does not prove equivalence. There is no CI speed threshold or automatic winner. The OFF arm does **not** reproduce the compiler's internal JSX caching: this is an ablation of one manual optimization, not a substitute compiler implementation.

## Architecture

All three apps nest `WorkspaceProvider` (queue), `IncidentProvider` (immutable updates), `FilterProvider` (search/status/sort), `SelectionProvider` (selected ID), and `ReviewProvider` (header counter). Incident and selection action contexts are separate from their data contexts, so unchanged rows do not subscribe to changing incident/selection data. The sidebar drills the active queue and selection action through `Sidebar` > `QueueNavigation` > `QueueItem` > `QueueIcon`, with a separate `SidebarFooter`; all queue icons use Lucide. The manual app memoizes queue items, provider values, callbacks, derived filtering, rows, and their open/favorite button components, while the compiler app uses no manual memo hooks. The repeated buttons receive named callbacks: manual stabilizes the callbacks with `useCallback`, while compiler and baseline leave them un-memoized. This makes callback identity meaningful across a component boundary without treating every inline DOM handler as a performance bug. Compiler and baseline import the same app and provider source; only the compiler's Vite plugin transforms it. The manual app keeps its explicit memoization boundaries. All three use the same un-memoized `Button`, `TextInput`, `Select`, and `StatusBadge` components, so new provider values and un-memoized rows expose the impact of omitting optimization without changing the workflow. No hook rules need inline lint suppression: baseline hooks follow the rules of hooks. Header-only reviews update the shell without updating rows. Queue, selection, favorite, resolution, search, status, and sort exercise the affected subtrees.

The compiler app opts in to `@vitejs/plugin-react`'s `compiler: { compilationMode: 'infer', logDiagnostics: true }` and pins compatible `oxc-transform-react`. Manual and baseline both use `react()` alone. Vite's ordinary Oxc TS/JSX transform runs for all three. This experimental integration is **not** the official Babel compiler; logged recoverable compiler diagnostics must be inspected, not silently treated as successful optimizations. Oxlint's opt-in React rules are explicit errors. Manual `memo`, `useMemo`, and `useCallback` imports are prohibited in compiler/baseline entry-source directories, `shared/**`, and `benchmark/recorder.tsx`, but remain legal in the manual app. Member restrictions also prohibit these property names on any object in the restricted files, including React aliases; this deliberately rejects unrelated properties such as `cache.memo` too. The native import rule also rejects React namespace imports even if only ordinary hooks are used, so prefer named imports, including for `Profiler` and types. Static computed members, destructuring and React re-exports are checked; indirect local-barrel imports and dynamic property keys are not resolved. These rules are a source convention, not transitive binding analysis. Isolated positive, negative, and mutation fixtures check the actual override scopes alongside the existing immutability guard. Normal production bundles are inspected for compiler cache transforms in toolbar, list, row, detail, and shell only on the compiler side, and must not contain profile instrumentation.

## Measurement

### Single-page comparison

The existing `report/` page and `benchmark/results/comparison.md` keep all three approaches side by side, in the same order: **No memoization / Manual memoization / React Compiler**. Jump links separate the overview, page load, row selection, query filtering, additional evidence, and methodology. The overview shows absolute results and optimized-minus-no-memo differences; negative bytes or milliseconds mean less, positive means more. Each row has its own endpoint and protocol, not an overall score or automatic winner. A zero reference has no percentage.

The overview also gives an evidence-based gist: manual memoization remains effective, selection timings do not establish a compiler/manual speed winner, and the measured minified-JavaScript delta determines which approach has lower bundle cost. The percentage and direction come from the current measured builds, not a fixed historical result. This is not evidence of equivalent responsiveness, identical memory behavior or guaranteed gains across workloads.

Page load contains shipped bytes, full-table readiness, load-window memory and Lighthouse. Selection and filtering each place normal-production response timings beside separately labeled profiling-build component work. Additional evidence keeps the remaining stateful workflows, favorite CPU/post-GC memory diagnostics and matching isolated row-memo evidence fully expanded. No favorite trace is presented as selection or filtering timing. The app and its optimization strategies are unchanged.

Normal Vite manifests define initial-load JS entry chunks, static imports, and attached CSS, each file counted once. Reports include raw and gzip JS, CSS, total, compiler-minus-manual, and optimized-minus-baseline byte/percentage deltas; source maps, dynamic imports, and profile builds are excluded. Separately loaded chunks are listed if present. This is shipped application size, not installed package size or an exported-module fixture.

Profile mode is a production build with `react-dom/client` aliased to `react-dom/profiling`. A shared `Profiled` helper places boundaries **outside** the measured components: one root around `App`, then shell, toolbar, list, detail, queue items, rows, and the repeated open/favorite buttons. Root includes provider render bodies; shell includes its filtering calculation; list includes row-element construction; detail includes its lookup. A boundary returned from inside its owner would miss that owner's preceding body work. These durations are inclusive and overlap: never add root, shell, list and row durations together, or interpret their differences as component self-time. Normal production builds omit enabled profiling instrumentation and supply shipped bytes, UPLT, Lighthouse, and 4x CPU traces.

Playwright runs one Chromium worker/browser; each app gets a fresh isolated context per profiling run, one warm-up, then three repetitions alternating app order. Each action waits for its semantic outcomes and completed root/diagnostic batches before capturing timing, fiber evidence and DOM state together. This is a completion contract for the current synchronous interactions, not an arbitrary timer/network settling detector; no-op actions can have zero commits, and incomplete batches are errors. Legacy search uses bulk input filling in the stateful workflow, while sort-and-reset is a multi-operation action. The independent filtering path uses sequential typing in a separate fresh context. Action clears preserve lifecycle counters so filtered-out rows remounting with the same ID are not confused with updates.

Raw measurements and comparison reports use `schemaVersion: 2`; regenerate older artifacts with `yarn benchmark` rather than mixing measurements across boundary definitions. Raw records retain `actualDuration`, `baseDuration`, `startTime`, `commitTime`, phase, root identity/generation, commit sequence and boundary generation. Whole-app commits come from distinct root records, not nested callbacks; root phases and mount durations remain separate from update summaries. `medianDurationMs` contains actual render-duration medians and `medianBaseDurationMs` contains estimated base-duration medians, with corresponding per-run `durationMs` and `baseDurationMs` fields. Missing observations are `null`; measured zero remains zero.

`actualDuration` measures the render work observed for the committed profiled subtree. `baseDuration` estimates a full-subtree render cost from components' most recently recorded render costs; it is **not** a second render with memoization disabled and does not reconstruct uncached `useMemo` or compiler computations. Their difference is not measured savings. Neither metric measures DOM commit work, layout, paint or end-to-end interaction latency. Both include profiling-context limitations and are advisory, not CI timing thresholds.

For row, queue and button render-work events, a test-only DevTools hook inspects React 19.3.0 profiling fibers: tag `12` identifies our `<Profiler>` boundary, its child is the component being measured, `alternate` excludes first mounts, and flags bit `1` indicates performed work. The probe validates supported child shapes and correlates work with completed commits, checking previous committed identity so reused bailout children do not count merely because old flags remain set. None of these fields or bit values is a public React API; revalidate this interpretation on each React upgrade. A component may contribute events in multiple commits. These supplementary counts are not additive, are not a complete invocation/aborted-render ledger, and do not measure equivalent-cost CPU operations or DOM mutations. Parity, row-edit sensitivity, header isolation, build/guard correctness, and nonzero measured bundle sizes are gates. Compiler improvements are not failures merely because an older compiler/manual count difference disappears.

The report explains the inspected Oxc output rather than claiming React Compiler cannot reproduce `memo` behavior. In the observed mapped list, the compiler caches the entire map against `incidents` and `selectedId` and caches child JSX inside rows; manual `memo(IncidentRow)` can avoid entering unchanged row bodies earlier. Equal compiler/baseline row-event counts can therefore coexist with fewer compiler child-button events. Report explanations use current counts and expanded source excerpts, and explicitly request reassessment if the generated-code pattern changes. Runtime conclusions remain separate from these diagnostics: all three approaches are compared by scenario, without inferring speed from fewer render events or size. Gzip remains a transfer-size metric, not parsing time. The isolated manual ON/OFF intervention does not model compiler caching or predict the effect of adding `memo` to the compiler arm.

UPLT (user-perceived load time) is measured on _normal_ builds as elapsed time from navigation start until all 200 rows have been rendered and two animation frames have elapsed, under a 4x CDP CPU throttle. It is a lab readiness proxy, not a Web Vital or guaranteed paint measurement. Six fresh contexts per app cover all six app-order permutations, with each implementation in each order position twice; the median and all six samples are reported. Run order is recorded in `slowdown.json`, and reporting rejects missing or unbalanced runs. A separate normal-build selection workload starts from 67 Platform incidents, warms each app, then times 20 detail opens with 4x CPU slowdown from the browser click handler to the detail DOM update and two animation frames later; closing is an untimed reset. Samples and p90 are reported without a CI speed threshold. The six UPLT runs also sample post-GC renderer JS heap after the table is ready and after a favorite edit, outside the timed load and CPU-profile windows; the paired favorite diagnostic reports all six runs. This measures JS heap only, not total browser/DOM/native memory or leak growth. First-run CPU profiles for the favorite action use that same throttle and yield SVG flame charts; the sampled span includes browser/idle work and is **not** a React render duration. Lighthouse 12 still runs three fresh mobile audits per app using its separate simulated throttling preset. FCP, LCP, TBT, Speed Index, CLS, interactive time, performance/accessibility scores and raw audit files are reported. Lighthouse simulations, CPU sampling, and local timings cannot prove real-user gains; no noisy timing is a CI performance threshold.

### Typed query filtering

Filtering starts independently from all 200 incidents, All statuses, newest sort and no selected detail. The query is typed as `A` then `AP` then `API`, followed by one clear operation: expected rows are **200 / 34 / 34 / 200**, with exact ordered incident IDs verified for every step in every arm. Each profiling run uses a fresh context; clearing remounts the 166 removed rows, separately from render-work updates. Raw profiling paths are additive `paths.filtering` fields under each app repetition in schema-v2 `measurements.json`.

Normal production timing uses separate isolated app contexts, one full warm-up and 20 warmed cycles at 4x CPU slowdown, rotating app order each cycle. Browser timers start on the native input event before React handles it. `AP` and clear have a result-DOM mutation endpoint followed by two animation-frame callbacks. `A` and `API` keep the same result IDs, so result-DOM timing is `null`, explicitly no result change, while input-to-two-frame opportunity is still captured. A frame opportunity is not guaranteed presentation or INP. This completion contract supports today's synchronous filtering, not future debounced/async searches.

Typing has at least 100 ms pacing per character, outside measured endpoints; setup, Playwright waits and clearing/reset time are not added to another step's timing. Median and nearest-rank p90 are computed independently per step across 20 cycles, never pooled across keystrokes or summed into a workflow total. Raw timings, step metadata, app order and browser/protocol identity are in `filtering-latency.json`, included in provenance, CI artifacts and Pages downloads. The combined summary retains these under `comparison.json.interactions.filtering` and native profiling under `comparison.json.paths.filtering`. Missing steps, wrong results, incompatible protocols or browsers fail reporting. Use `yarn benchmark:all` to regenerate matching complete evidence; `yarn typecheck:measure` checks the measurement harness explicitly.

### Load-time memory

The report separately measures **JS heap used** (`Runtime.getHeapUsage.usedSize`) and **embedder heap used** (`embedderHeapUsedSize`) during normal-production loads. The latter is the embedder's garbage-collected heap, including Blink-managed objects, not all native/DOM allocations or total tab/process memory. The protocol reports the corresponding isolate, not only React or one JavaScript execution context. `totalSize` (allocated JS heap) and `backingStorageSize` (array-buffer/external-string storage) are preserved separately, never summed into an invented total. See the [CDP definitions](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#method-getHeapUsage).

The memory-only workload runs six repetitions per app using all six order permutations and a fresh Chromium browser/context for every load, with cache disabled, a 1440x900 viewport and 4x CPU slowdown. It samples from navigation until the full 200-row table has completed two animation-frame callbacks, then records a readiness snapshot **before forced GC** and another after `HeapProfiler.collectGarbage`. A blank-page snapshot is retained for context, not subtracted from app memory across potentially different isolates. No DevTools backend, React profiling instrumentation, CPU profiler or forced GC runs during the load window. Memory polling is kept out of the existing latency runs.

The requested sampling pause is 20 ms **after each CDP response**, not guaranteed fixed-rate sampling. CDP round-trip delays and main-thread scheduling can miss peaks; the raw data brackets each request with host-clock timestamps. The reported sampled peak includes the readiness snapshot and is an observed maximum, not the true allocation peak. Each counter's maximum is computed separately. Natural GC can occur before any snapshot; pre-forced-GC usage includes unreachable objects and GC-timing noise, while the post-GC value is a separate retained-memory diagnostic, not a leak test or perfect census of live memory.

The main report shows medians and observed min/max in baseline-first columns, manual/compiler percentage differences against no memoization, and the explicitly labeled compiler-minus-manual comparison. Percentages use each unrounded reference median. Zero reference counters yield an explicit unavailable percentage, not zero or infinity. Missing protocol counters or mismatched browser/design data fail with diagnostics. Six local loads are descriptive, not statistical proof of a compiler advantage; fresh browser/cache runs do not reset OS/disk caches.

Raw counters, sample timestamps, readiness observations, run order and snapshots are in `benchmark/results/load-memory.json`, included in provenance, CI downloads and Pages. `comparison.json.loadMemory` retains per-run summaries and deltas; the older `memory` field remains the separate `Performance.JSHeapUsedSize` post-GC before/after-favorite diagnostic. To run only the new browser workload against existing normal builds, use `yarn playwright test benchmark/load-memory.spec.ts`; use `yarn benchmark` (or `yarn benchmark:all`) to regenerate matching published reports and provenance.

GitHub Actions runs `yarn benchmark:all` for pushes and pull requests. Download the `compiler-comparison` artifact for the main and ablation reports, source snapshots, provenance, linked flame charts, CPU profiles, load-memory measurements, and raw audits; failed runs also upload `playwright-diagnostics` when available.
